Context
- Issue #16: offline / network-unavailable device behavior. This affects degraded-mode UX, retry/backoff, and M4 acceptance criteria.
- Current repo notes: issue body describes purpose and acceptance criteria but lacks a recorded decision and owner.

Options

1) Graceful degraded mode with cached operations and local queueing
- Pros: best UX offline; allows user tasks to continue and sync later; simpler rollout.
- Cons: more local state to manage; complexity in conflict resolution; storage and privacy considerations.

2) Minimal offline mode: read-only UI, queue critical writes only, show clear offline messaging
- Pros: low implementation complexity; reduces conflict risk; predictable behavior.
- Cons: reduced UX compared to full caching; some user flows blocked.

3) Fail-fast with immediate error surfaces and retries only when user retries
- Pros: simplest to implement; forces explicit retries.
- Cons: poor UX; likely higher support cost.

Recommendation
- Choose Option 2 (Minimal offline mode) as a conservative, low-risk default that preserves core safety and reduces complex sync/merge work. Implement local queueing for critical writes only, with explicit user-facing messaging and a clear retry path.

Owner
- Provisional owner: @dmd0822. If a different owner is preferred, update the issue's assignee.

Consequences
- Implementation work scoped to a small offline surface area; lower immediate QA burden.
- Future enhancements may expand to Option 1 if usage/requirements justify the added complexity.
