# UD-07 — Conversation retention decision

Status: Accepted
Related issue: #17
Decision owner: @dmd0822 (provisional)
Target resolution date: 2026-09-22

## Context
Purpose: define whether the device retains conversations or other state across sessions and how it is deleted. Context: this decision is tracked from issue #1 and affects privacy, RAI, and the data-management plan. Acceptance criteria: the retention policy is recorded, the decision is linked from the M0 tracking doc, and any follow-up policy or implementation work is captured.  Decision record (draft): https://github.com/dmd0822/sparky/blob/resolve/ud-07/.squad/decisions/ud-07.md

## Options

### Option A — No persistent retention
- Description: Do not persist conversations beyond the active device session. All conversation state is in-memory and cleared on app/device restart or explicit user action.
- Pros: Best privacy and compliance posture; minimal RAI surface; simplest to audit and implement.
- Cons: Reduced UX continuity across sessions; users cannot resume past conversations.

### Option B — Short-term ephemeral retention with TTL (Selected)
- Description: Retain conversations for a short configurable TTL (e.g., 24–72 hours) encrypted at rest; auto-delete after TTL and allow explicit user deletion.
- Pros: Balances UX and privacy; allows short-term resumption.
- Cons: Increased compliance burden; requires secure storage and deletion support.

### Option C — Persistent retention with explicit opt-in (Deferred)
- Description: Persist conversations until user deletes them; retention enabled only after explicit consent and visible controls.
- Pros: Best UX for continuity and features that rely on history.
- Cons: Highest privacy and RAI risk; requires robust policy, consent tracking, and deletion workflows.

## Recommendation
Option B is selected (short-term ephemeral retention with TTL). Option C is explicitly deferred for later consideration if product needs justify persistent retention and consent/deletion controls are implemented.

## Owner
Provisional owner: @dmd0822

## Consequences
- Implementation: Add secure, encrypted short-term storage with TTL and automatic deletion, plus UI controls for explicit deletion. Ensure audit logs for retention/deletion actions.
- Policy: Update M0 tracking doc and any privacy/RAI artifacts to reflect TTL, encryption, and deletion workflows.
- Follow-ups: Create tasks for storage implementation, encryption, consent tracking (if any), and verification/testing. Revisit Option C when requirements emerge.
